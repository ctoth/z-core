## Findings and decisions

- Replay must record ordered external bus reads and writes. Historical replay
  supplies recorded read values, validates writes, and suppresses calls to the
  live bus so device state is not mutated twice.
- Save states exclude the host bus and external mapper. The first replay
  format is therefore an in-process timeline; backward playback is supported,
  but branching a new live future is forbidden unless the host separately
  restores its device state.
- `try_step` is not atomic on host-bus failure. Effects completed before the
  failing bus access can remain even though registers are restored and zero
  cycles are charged. Timeline positions therefore count every attempted
  step, including failures and zero-cycle sleep attempts.
- Replay step ordinals belong to timeline checkpoints, not `Z180` save state.
  `z180-core` and save-state version 4 remain unchanged.
- The published `v0.1.0` tag already produced state version 4, and its
  `SavedState` schema matches current `master`. The compatibility fixture will
  be generated by the tagged code and current code must load and re-save it
  byte-for-byte.
- The existing Python `nightly` Hypothesis profile already means 50,000
  examples per property. Its strategies cover single Z180 instructions,
  sequences up to 32 instructions, undefined-opcode TRAPs, and all 16 MMU
  pages. The scheduled workflow will run that exact profile.
- `find_first_write` will be a temporary probe: save the current state and
  replay cursor, seek, install a memory watch, drain per attempted step, then
  restore the original state and mode unconditionally. Event loss is an
  explicit error.
